# 通信費インデックス（tsushinhi-index）

日本の通信費（光回線・格安SIM）の**料金と条件を毎日自動で記録し続ける公開データセット**です。

各社の料金は頻繁に変わりますが、**「いつ・いくらから・いくらに変わったのか」を横断的に記録した公開データは存在しません。**
このリポジトリはその空白を埋めることを目的にしています。

## なぜ作るのか

光回線の実質的な負担額は、月額基本料だけでは決まりません。

- キャッシュバックの**額と受取時期**
- 適用に必要な**必須オプション**
- 工事費の**実負担額**と途中解約時の残債
- 契約期間

これらの組み合わせで決まりますが、**各社が自社に有利な計算で「実質料金」を出している**ため、横並びの比較が成立していません。
さらにこれらは頻繁に変わります（実測: ある事業者の料金ページは**年59回**内容が変わっていました）。

**このデータセットは、全社を同一の計算式に通した「実質月額」を毎日記録します。**

## 実質月額の計算式

```
実質月額 =
  ( 月額の合計
  + 工事費の実負担額
  + 事務手数料
  + 必須オプション費用 × 加入必要月数
  - キャッシュバック額
  - その他割引の総額
  ) ÷ 契約月数
```

**計算ルール**

- 月額は期間ごとに変わるため（例: 1か月目 / 2〜24か月目 / 25か月目〜）、**月単位に展開して合計**します。平均や代表値は使いません
- 全社を横並びにできるよう **36ヶ月を主軸**とし、24ヶ月も併記します
- キャッシュバックは**受取時期が計算期間を超える分は算入しません**（受け取れない可能性があるため）。除外した分は `excludedCashback` に残します
- 必須オプション（キャッシュバック適用に加入が必要なもの）は費用に**算入**します。任意オプションは算入しません
- 工事費は「分割請求額の合計 − 割引の合計」を実負担とします。計算期間が分割回数より短い場合はその時点までで計算します
- **値が取得できなかった項目は推定しません。** `null` を入れ、実質月額も `null` にします
- 端数は円未満を**四捨五入**します

最後から2番目のルールが最も重要です。**欠損を推定で埋めた時点で、このデータは信用に値しなくなります。**

### 事業者間で揃えていること

同じ「36ヶ月」でも、各社の数え方・載せ方が違います。揃えずに並べると比較が成立しません。

| 揃えている点 | なぜ |
|---|---|
| **契約1か月目 = 開通月** | NURO光は開通月を「1か月目」と呼び、So-net光は「開通月」と「1カ月目」を別に数えます。揃えないと**片方だけ開通月を含む36か月**を比べることになります |
| **開通月は各社が公開している上限額を使う** | 開通月は日割りで確定しません。上限を使うので**高く見積もる側**に倒れます（安く見せる誤りを作らない） |
| **キャッシュバックは掲載場所を問わず算入する** | NURO光は料金内訳表の中に、So-net光はページ上部の特典表にあります。片方だけ拾うと、拾えなかった側が不当に高く見えます |
| **他サービスの契約が前提の割引は算入しない** | 楽天ひかりの「最強おうちプログラム」（楽天モバイル契約が前提）、NURO光の「NUROでんき／ガスとのセット割」などです。算入すると**その契約にかかる費用を無視して安く見せる**ことになります。事実としては `setBenefits` に残します |

### 何で検算したかを観測ごとに記録しています

検算の手段は事業者によって異なります。**弱い検算しかできない事業者を、強い検算ができたかのように扱いません。**

| 事業者 | 検算の方法 |
|---|---|
| NURO光 / So-net光 | 内訳から計算した月額と、ページが公開している適用後の月額を突き合わせ |
| 楽天ひかり | ページに適用後の月額が無いため突き合わせ不可。税抜×1.1=税込、工事費の分割×回数≈一括 の内部整合で検算 |

各観測の `verificationMethod` に何で検証したかが入っています。

### 計算結果を機械的に検算しています

各社の料金ページには、内訳（月額基本料金・工事費・割引）と、その適用後の月額の**両方**が載っています。
このデータセットは内訳から月額を計算し、**ページが公開している月額と一致するかを毎回突き合わせます。**

一致しない観測は `verified: false` として記録し、**変化の検知には使いません。**
読み方を間違えたまま「値上げしました」と発信しないためです。

ページ内で記載が食い違う場合（例: ページ全体のキャンペーン表と、個別プランの料金内訳表でキャッシュバックの有無が違う）も、
どちらかを黙って採用せず `ambiguities` に食い違いの内容を残します。

## データの扱い方針

- **出典URLと取得日時を全レコードに記録**します
- **取得に失敗したとき、前回の値を引き継ぎません。** 失敗は失敗として記録します
- 収集対象は**各社が一般に公開している情報のみ**です。ログインが必要な情報は収集しません
- **自動アクセスを望まない意思表示があるサイトは対象にしません。** robots.txt での禁止に加え、bot対策で保護されているサイトも、技術的に回避できるかどうかに関わらず除外しています
- 収集するのは**料金・日数・条件といった事実値のみ**で、説明文などの表現をそのまま複製・再掲することはしません
- 相手サーバーに負荷をかけないよう、アクセスは低頻度・直列で行います

## 収集元

`collect/targets.json` に、対象事業者と参照しているURLをすべて記載しています。

収集は3系統で行います。

| 系統 | 対象 | 取れるもの | 出力 |
|---|---|---|---|
| **主: お知らせ監視** | 各社公式の「料金改定のお知らせ」ページ | **正式な適用日・変更理由** | `data/notices/` |
| 従: 料金ページ監視 | 料金・キャンペーンページ | 掲載値がどこか変わったこと | `data/prices/` `data/changes/` |
| **実質月額** | 料金表ページ（各社アダプタ） | **実質月額と、その変化幅** | `data/effective/` `data/effective-changes/` |

お知らせを主系統にしているのは、料金ページの差分だけでは「気づいた日」しか分からず、**正式な改定日と変更理由が取れない**ためです。

料金ページ監視と実質月額を分けているのは、**言えることの強さが違う**ためです。
前者は「どこかの数字が変わった」までしか言えません。後者は「**実質月額が◯円上がった**」と言えます。
後者には各社ごとのアダプタ（`collect/adapters/`）が必要で、対応できた事業者から順に増やしています。

### 収集元は「正規の料金表ページ」を使います

トップページや訴求ページは A/B テストや季節バナーで表示が変わるため、時系列の土台になりません。
実際、ある事業者のトップページは1回の取得の中に**10通りの表示変種**を含んでいました。
そのため収集元には、プランごとに分かれた正規の料金表ページを使っています。

## 検証

```
node --test collect/test.mjs
```

計算ロジックの自己テストです。日次ワークフローでも**収集の前に**実行し、
壊れたロジックのまま `data/` に書き込まないようにしています。

## 免責

このデータは正確性を期して自動収集していますが、**契約前には必ず各社の公式サイトで最新の条件をご確認ください。**
各レコードには出典URLと取得日時が記録されています。
